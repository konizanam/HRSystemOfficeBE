# Assumptions

This file lists every **ASSUMPTION** from `BUILD_SPEC.md`, plus the decisions taken during the build where the spec was silent. The open points in spec section 18 still need confirmation from the business.

## From the spec

The default is 1 (direct reports only).                                                                                                                                                                                                         | §4.1   |

## Build decisions

| #   | Area               | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| --- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| B1  | Repositories       | The spec describes one monorepo. This build uses two repositories: **HRSystemOfficeBE** holds `apps/api` and `packages/shared`, and **HRSystemOfficeFE** holds `apps/web` and a synced copy of `packages/shared` (`pnpm sync:shared`). Both use pnpm workspaces and Turborepo.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| B2  | Database           | The local development cluster is PostgreSQL 18. CI uses PostgreSQL 16 as the spec requires. The schema uses no features newer than 16.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| B3  | Integration tests  | Docker is not available on the development machine, so integration tests use `TEST_DATABASE_URL` (a dedicated `peoplehub_test` database). When that variable is unset, they fall back to Testcontainers (Postgres 16). The test setup runs `prisma migrate deploy`, which is non-destructive. Tests use unique keys and never assume an empty database.                                                                                                                                                                                                                                                                                                                                                                                                       |
| B4  | Audit chain        | Each row's `id` is taken from the sequence under the advisory lock, so it is included in the hash. Rows are buffered during the business transaction and appended as its last statement.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| B5  | Audit safety net   | An upsert that leaves a row unchanged does not produce a generic `DATA_CHANGE` row, so idempotent seeds stay quiet.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| B6  | Audit anchors      | `AuditAnchor` is append-only, with the same trigger as `AuditLog`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| B7  | SYSTEM actor       | A built-in `SYSTEM` user (`00000000-0000-0000-0000-000000000000`, inactive, no password) is created by migration. Jobs and automatic workflow actions use it as the actor.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| B8  | Idempotency        | Replays are stored in the extra `IdempotencyRecord` table. The key is scoped to user + method + route. A concurrent replay while the first request is running gets 409.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| B9  | Validation status  | Request-body schema violations return **422** with field errors, the same as business validation, so the web app maps both to fields the same way.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| B10 | Append-only tables | `LeaveLedgerEntry`, `WorkflowAction`, `AuditLog` and `AuditAnchor` have `UPDATE`/`DELETE`/`TRUNCATE` revoked from `app_user` and are blocked by triggers.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| B11 | Email              | Development SMTP settings are taken from the existing HR project (`smtp.gmail.com:465`). Tests use an in-memory transport (`MAIL_TRANSPORT=memory`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| B12 | Libraries          | `nestjs-zod` 5.5 is used because 4.x is incompatible with `@nestjs/swagger` 11. Zod 3.25 is used throughout. `fastify` is pinned to the version `@nestjs/platform-fastify` uses.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| B13 | Session activity   | The idle deadline moves on `POST /session/activity` and on every state-changing request (POST/PUT/PATCH/DELETE). Plain reads do not count, so background polling cannot keep an unattended session alive. Timeouts (idle or the 12-hour absolute lifetime) are audited `AUTH.SESSION_TIMEOUT` with `metadata.reason` `IDLE` or `ABSOLUTE`.                                                                                                                                                                                                                                                                                                                                                                                                                    |
| B14 | Company scope      | HR and Payroll admins administer the company of their own employee record. An admin with no employee record administers every company. Auditors read across all companies (scope purpose `AUDIT`). Multi-company admin assignments are left for the admin phase.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| B15 | Session cookies    | `ph_session` holds a random token and the `Session.id` is its sha256, so neither the database nor the audit trail holds a usable cookie. CSRF uses double submit, and the header must also equal the token stored on the session. Cookies are `Secure` unless `COOKIE_SECURE=false` (local http only).                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| B16 | Rate limiting      | Every `/auth/*` handler carries the same `@fastify/rate-limit` route config (10 requests per minute per IP). Each route counts separately. The client IP comes from `X-Forwarded-For`, because the API runs behind a proxy (`trustProxy`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| B17 | Auth audit rows    | A failed sign-in writes `AUTH.LOGIN_FAILURE` (no actor, the targeted user as entity, the attempted username in metadata) and a timeout writes `AUTH.SESSION_TIMEOUT`. These replace the generic `SECURITY.ACCESS_DENIED` row for those 401s; every other 401/403 still writes it. Wrong current passwords on change are audited `AUTH.PASSWORD_CHANGE_FAILED`.                                                                                                                                                                                                                                                                                                                                                                                                |
| B18 | Lockout            | The fifth consecutive failure (wrong password or wrong TOTP code) locks the account for 15 minutes and resets the counter. Attempts during a lock do not extend it. The sign-in error says the account is locked. A password reset clears the lock.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| B19 | Passwords          | The history of 5 includes the current password: it and the four before it cannot be reused. A password may not contain the username (3 or more characters). A change signs out the user's other sessions; a reset signs out all of them. Password change counts as the `PASSWORD` restricted feature, so it is refused while working as someone else.                                                                                                                                                                                                                                                                                                                                                                                                         |
| B20 | MFA                | `User.mfaEnabledAt` was added. Enrolment stores the encrypted secret but MFA stays off until a code is verified (`AUTH.MFA_ENROLLED`). Re-enrolling while MFA is on returns 409; turning it off is an admin action (Phase 9). OAuth accounts cannot enrol (the identity provider handles MFA). One 30-second step of clock drift is accepted.                                                                                                                                                                                                                                                                                                                                                                                                                 |
| B21 | Setup mobile       | `MobilePairingToken` was added (sha256 of the token only, 5-minute expiry, `usedAt` for single use). The QR code encodes `peoplehub://pair?server=<PUBLIC_URL>&token=<token>`. Issuing is audited `AUTH.MOBILE_PAIRING_CREATED`. Redeeming the token belongs to the mobile app work and is not built yet.                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| B22 | OIDC               | State, nonce and the PKCE verifier travel in a 10-minute `ph_oidc` cookie encrypted with the AES-GCM field key. The callback redirects to `PUBLIC_URL` + `returnTo` (default `/dashboard`) or to `/login?error=<code>`. Users are matched only by `externalSubject`, never by email. Auto-provisioned users get the `EMPLOYEE` role and no employee link. An `http://` issuer is refused in production.                                                                                                                                                                                                                                                                                                                                                       |
| B23 | Settings           | `workflow.autoProcess.*` has one key per payroll-processed type (LEAVE, CANCELLEAVE, CLAIMS, GROUPEDCLAIM, CREDITLVEALLOC, CREDITLVEREQ). `mail.from` = null falls back to `MAIL_FROM`. `ui.accentColour` and `ui.helpUrl` were added. Saving an unchanged value writes and audits nothing. Other API instances see a change within 30 seconds (cache TTL).                                                                                                                                                                                                                                                                                                                                                                                                   |
| B24 | Working as         | Only users with the `MANAGER` role act for reports, and `HR_ADMIN` for anyone in their companies. The stored choice is re-checked on every request; if it is no longer allowed, the session falls back to self and the change is audited automatically. Switching to self writes no audit row. For HR admins the options list is capped at 200 rows with a `search` filter.                                                                                                                                                                                                                                                                                                                                                                                   |
| B25 | Seed               | The spec does not place the four admins in the hierarchy; they report to manager A. Seeded emails use the reserved `peoplehub.example` domain. Existing seeded rows are never updated, so a password changed in development survives a re-seed. `employee1` has entity code `000077` and employee code `E000077`.                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| B26 | Email              | Request handlers send email in the background; a mail failure is logged (without the recipient) and never fails the request or reveals whether an account exists. Password reset links point at `PUBLIC_URL/reset-password?token=…`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| B27 | Workflow schema    | Phase 3 adds `StepStatus.SUPERSEDED`, `WorkflowStepInstance.escalatedAt`, `OutboxEvent.attempts`/`lastError` and `OutOfOfficeRule.deletedAt` (rules are soft-deleted and revived through their unique key, so no business row is hard-deleted).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| B28 | ROLE steps         | A ROLE step gets one PENDING instance per role holder, so it shows in each holder's Action Required. The first to act wins: their instance records the action and the others become `SUPERSEDED`. Holders are active users with the role whose employee record is ACTIVE in the applicant's company; admins without an employee record are never role candidates (they can still be `SPECIFIC_USER` approvers). The holder list is taken when the step is assigned.                                                                                                                                                                                                                                                                                           |
| B29 | Segregation        | The "applicant" is the subject employee's user **and** the submitter. Neither can approve, be reassigned the step or be an out-of-office nominee for it. A manager who submits for a report is therefore skipped at their own REPORTS_TO step.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| B30 | Definitions        | The most specific active definition wins: a discriminator match outranks a company-rule match, which outranks the type-wide default; ties go to the highest `versionNo`, then the newest. A mandatory step that resolves to nobody goes to the HR admins of the applicant's company (audited with `usedFallback`); with no HR admin either, the submit or approval fails with 422 (`urn:peoplehub:problem:workflow-no-approver`). For a ROLE step, `skipIfSameApprover` removes the previous step's approver from the candidates and skips only when nobody else holds the role.                                                                                                                                                                              |
| B31 | Completion         | Payroll types are the six in `PAYROLL_PROCESSED_WORKFLOW_TYPES`; every other type (including TRAINING, QUALIFICATION and JOBREQUISITION, which section 7.2 does not list) completes on the last approval with an `APPLY` action (`WORKFLOW.APPLIED`). `workflow.autoProcess.{TYPE}` uses the open pay period of the employee's company rule that contains today, else the next open one; with none, the item stays pending and `WORKFLOW.AUTO_PROCESS_SKIPPED` is audited. Processing needs an open period of the employee's company rule and a payroll admin of the employee's company. A handler's `onFinalApproval` may return `CONFLICT` (the ChangeRequest pattern), which ends the process in `CONFLICT` and alerts HR.                                 |
| B32 | Versions           | Every user action (including COMMENT and PARK) increments the process `version`; system bookkeeping (the escalation flag, unparking) does not, but an automatic reassignment does. Authorisation is checked before the version, so only someone involved in the process learns that a version is stale (409); everyone else gets 403.                                                                                                                                                                                                                                                                                                                                                                                                                         |
| B33 | Parking            | `until` is a business date; the step returns at the start of that day (Africa/Windhoek), at most 365 days ahead. Parking hides only the parker's instance. The parker can still act from the detail panel; a due item shows in Action Required straight away, and the 15-minute job sets it back to PENDING, restarts the escalation clock and notifies the assignee.                                                                                                                                                                                                                                                                                                                                                                                         |
| B34 | Escalation         | The assignee and their manager are notified once per step instance (`escalatedAt`). With `workflow.escalation.autoReassign`, a step still pending at `dueAt + escalationHours` (twice the time from assignment) moves to the applicant's second-level manager, unless that person is unavailable, already an approver of the step or the applicant.                                                                                                                                                                                                                                                                                                                                                                                                           |
| B35 | Re-resolution      | "Unavailable" means an inactive user or an employee record that is not ACTIVE (suspended included) or is deleted. A ROLE step with another available candidate just drops the instance; otherwise the step rule is applied again (HR fallback for a mandatory step, skip for an optional one). A step that still cannot be resolved is left and logged. The nightly job runs at 02:30; `WorkflowEngine.reresolveForUser(userId)` is the hook for the employee termination flow.                                                                                                                                                                                                                                                                               |
| B36 | Out of office      | Delegation is applied whenever a step is assigned (submit, next step, resubmit, reassignment, escalation, re-resolution), not to steps assigned earlier. Nominees must be active users in the same company and never the user; an inactive nominee counts as none. WHILE_ON_LEAVE uses approved or processed leave covering today, ignoring CANCELLEAVE applications. The settings belong to the signed-in user; all three endpoints are refused while working as someone else. After three hops the third nominee keeps the step; a cycle leaves it with the original approver, audits `WORKFLOW.DELEGATION_CYCLE` and notifies the HR admins. A delegated nominee gets only the delegation notice.                                                          |
| B37 | Outbox             | Each event is delivered in its own transaction (`FOR UPDATE SKIP LOCKED`); listeners write in that transaction and email goes out after it commits. After 10 failed attempts an event is left with `lastError`. The `outbox.publish` job runs every minute and is also queued right after every workflow commit when jobs are enabled; it does not write `SYSTEM.JOB_RUN` rows (plumbing, not a business job). `DbService.afterCommit()` was added for that kick.                                                                                                                                                                                                                                                                                             |
| B38 | Notifications      | In-app notifications belong to the signed-in user, not the "Working as" employee. The in-app text names the applicant and quotes a decline or send-back comment; email carries only the first name, the request type and a link to `PUBLIC_URL/inbox/items/{processId}`. Nobody is notified of their own action. A cancellation notifies the assignees of open steps and the applicant/submitter.                                                                                                                                                                                                                                                                                                                                                             |
| B39 | Inbox              | Action Required = the signed-in user's open steps. Submitted = in-flight requests about the "Working as" employee (plus, when not acting for someone else, requests the user submitted for others). History = finished requests of the same set plus every request the user approved, declined, reassigned, sent back, parked or commented on. `box=process` (PAYROLL_ADMIN) lists items waiting for processing. DRIVERSLICENSE counts under Personal Details; TRAINING and QUALIFICATION under an extra "Other" category. The Approvals panel shows for MANAGER, HR_ADMIN and PAYROLL_ADMIN, or anyone ever assigned a step. A category is "enabled" when one of its types is active and has an active definition for the acting-as employee's company rule. |
| B40 | Process access     | Readers: the applicant, the submitter and anyone "Working as" the applicant; every approver (assigned, delegated from, or acted); HR and Payroll admins of the applicant's company; auditors. System admins are not readers. The applicant (or submitter) withdraws and resubmits; the applicant and approvers comment.                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| B41 | History text       | Only the APPROVED_PENDING_PROCESS sentence was observed. The other status sentences, the process-level lines (RESUBMITTED, WITHDRAWN, CANCELLED, PROCESSED, COMPLETED, CONFLICT), the step lines for reassign, delegation, park, unpark, escalation, auto-skip and comments, and a "Comment: …" line under an action with a comment are additions in the same style. "Remaining Approvers" is left out when nothing is outstanding; a later ROLE step shows "Any {Role}".                                                                                                                                                                                                                                                                                     |
| B42 | Workflow endpoints | Added to section 12.7: `POST /workflow/processes/:id/comment`, `GET /workflow/can-start`, `GET /workflow/pay-periods` (PAYROLL_ADMIN), `GET /workflow/user-options` (reassign picker) and `GET /profile/out-of-office/nominees`. Every workflow POST accepts `Idempotency-Key`. Bulk approve and process run one transaction per item and answer 200 with per-item results; a per-item 403 is audited as `SECURITY.ACCESS_DENIED` with `bulk: true`.                                                                                                                                                                                                                                                                                                          |
| B43 | Workflow seed      | The default definitions have company rule null and the name "Default approval"; an existing default is never touched, so HR edits survive a re-seed. Pay periods are named "{Month} {year}" with the pay date on the last day. A type without a registered subject handler uses a generic one that describes the request by its summary.                                                                                                                                                                                                                                                                                                                                                                                                                      |
